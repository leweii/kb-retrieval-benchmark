# KB Baseline 实验计划（v2）

## 结果（2026-11-11 题库审计后；完整报告：`report.html`）

- **推荐：DeepSeek V4.1 Flash + 智能体 · grep**（900 / 3000 篇首选；300 篇 LLM-wiki 导航 95% vs grep 89%，差 2 道题，不显著）。
  S3000：MuSiQue 准确率 88%、说不知道 90%、$0.0043/题、p50 61s。
- 关键对比（S3000，115 道干净题，配对精确 McNemar，21 个比较做 Holm 校正，见报告附录"显著性与稳健性"）：
  - **DeepSeek grep 88% vs Sonnet grep 84%：不显著**（p=0.39，校正后 1.0；按题目簇自助的差值区间 [-3, +9] 个百分点）。审计前的
    "70% vs 62%，p=0.015"主要来自金标有问题的题。
  - DeepSeek vs Haiku grep（88% vs 67%）、DeepSeek 智能体 grep vs 单次增强混合（88% vs 72%）、Sonnet 智能体 grep vs Sonnet 智能体混合
    （84% vs 72%）：校正后仍显著。智能体 grep vs 两轮混合（88% vs 83%）不再显著。300 篇只有 38 道配对题，所有比较都不显著。
- "找全证据"包含 grep 命中行，随搜索次数机械增长，不能说明 DeepSeek "搜得更彻底"；只算打开阅读也不对（Sonnet grep 准确率 84%，
  全部证据都打开过的只有 9%，多数直接用命中行作答）。DeepSeek 智能体 27% 的运行用满 12 步（Claude 1%），结果对步数上限敏感。
- 题库审计（2026-11-11，见 `report/audit_impact.md`）：MuSiQue 金标盲审删 56 道、补别名 28 道；不可回答题第二轮泄漏检查（按最后一跳检索、
  BRIGHT 不再截断文档、人工复核）按体量再排除一批。有效题 415 → 352，干净 MuSiQue 题 168 → 115。没有回答的运行改为按失败计。
- 未修（不重跑）：300 / 900 篇里几乎没有同题易混淆文档（金标占全库 72% / 65% / 20%）；NoLiMa 扩展植入句与核心同模板，20 道中 15 道
  有多个合法答案；DeepSeek / Haiku 的闭卷过滤是事后补测且 DeepSeek 有 24 条空预测；思考强度 Claude medium vs DeepSeek high。
- 规模：3 个模型 × 11 种配置 × 三档体量，31,713 条全部评分。花费：Claude 约 $823（含审计 $32），DeepSeek API $61。千问未参与。
- 复现：带评分的结果归档在 `data/results/p2_judged.tar.gz`；`harness/build_html.py` 生成 `report.html`；`uv run pytest` 跑计分测试。

## 0. 要回答的问题

> 知识库有 300 / 900 / 3000 篇文章时，**用什么检索方式、配什么模型、要不要接智能体、要不要先 digest 成 LLM-wiki**？

最终交付一张推荐表（§8）：每个体量给出首选方案、性价比方案，以及"不要这么做"的反例。

### v1 → v2 变更（2026-11-10）
- **放弃 RepliQA / MultiHop-RAG 题库**：它们是"看着文档出题"的阅读理解题（题目实词 80%+ 原样出现在证据文档里），
  BM25 在 3000 篇中召回 100%，无法区分检索方式。详见附录 A。
- 改用经过**区分度检查**的数据集：MuSiQue（多跳）+ BRIGHT（真实论坛提问、长文档）+ NoLiMa（无字面线索的联想）。
- 中文题 = 上述题目翻译成中文去查英文知识库（中文真实查询数据集 DuRetrieval / T2Retrieval 词汇重叠 83–100%，太简单）。
- 体量设计从"所有题的证据都在 S300"改为"核心题 + 扩展题"（多跳题证据文档太多，放不进 300 篇）。

### v0 → v1 变更
- 语料改用**公开数据集**（RepliQA 主线 + MultiHop-RAG 多跳副线），不再用团队 KB 做主实验。
- 检索方式收敛到 6 种：grep / BM25 / 混合 / 增强混合（QMD 式，全 API）/ LLM-wiki 导航 / LLM-wiki + 混合。删除 Contextual Retrieval、GraphRAG、整库塞上下文。
- digest 不再是独立维度，只作为 LLM-wiki 两种检索方式的前置步骤。
- embedding 走 API（OpenRouter），不装向量数据库。
- 提问 中英混合。
- 先跑 Claude（Anthropic API），再跑 DeepSeek（官方 API）和千问（OpenRouter）。

## 1. 语料与题库（v2）

### 1.1 区分度检查结果（`scripts/check_datasets.py`，`scripts/closed_book.py`，结果在 `report/`）
每个数据集抽 100 题，配约 3000 篇同领域文档，Recall@10：

| 数据集 | 题目实词出现在证据中 | BM25 | 向量 | 闭卷可答（Haiku 5.5） | 结论 |
|---|--:|---|---|---|---|
| **MuSiQue**（维基，2–4 跳） | 60% | 任一证据 97%，**全部证据 31%** | 任一 100%，**全部 52%** | ~17% | ✅ 主力：单次检索难以找全证据 |
| **BRIGHT**（StackExchange 真实提问，网页长文档） | 57% | **45%** | **86%** | 39% 完全答对 + 52% 部分 | ✅ 区分关键词 vs 向量；不评答案准确率 |
| **NoLiMa**（小说 + 植入句） | 20% | 0% | 2% | 不适用 | ✅ 小型探针：只有会推理的智能体可能找到 |
| 2WikiMultihopQA | 67% | 全部证据 53% | 全部 66% | – | 一般（模板题），不用 |
| HotpotQA / SciFact / DuRetrieval / T2Retrieval | 58–100% | 90–100% | – | – | ❌ 太简单 |

（对照：v1 的 RepliQA 英文题 BM25 = 100%。）

### 1.2 文档（"篇"）来源
| 来源 | 一篇是什么 | 中位长度 | 占 S3000 目标比例 |
|---|---|--:|--:|
| 维基页面（MuSiQue dev） | 同一标题下的段落合并成一页 | 短（几百到一两千字符） | ~55% |
| BRIGHT 网页（biology、earth_science、economics、psychology、robotics、stackoverflow、sustainable_living） | 一个网页原文（含导航、JSON 等噪声） | ~1.3 万字符 | ~35% |
| 小说片段（NoLiMa 书本） | ~500 词一段，NoLiMa 的植入句插在其中 | ~2.7k 字符 | ~10% |

一篇一个 `.md`：frontmatter（title / source / domain）+ `# 标题`，按 来源/领域 分文件夹。

### 1.3 体量与题目（核心题 + 扩展题）
- **核心题（约 150）**：证据文档放进 S300，三档都问 → 配对比较体量的影响。
- **扩展题（约 300）**：证据文档从 S900 开始放入，在 S900 和 S3000 问 → 增加统计功效。
- 一道题的证据只占全库很小一部分；其他题的证据文档天然就是同领域干扰文档。
- S3000 = S900 + 同领域填充文档（维基页面、BRIGHT 网页、小说片段），嵌套关系 S300 ⊂ S900 ⊂ S3000。

| 题组 | 核心（S300 起） | 扩展（S900 起） | 评什么 |
|---|--:|--:|---|
| MuSiQue 可回答 | 60 | 140 | 答案准确率（短答案）、找全证据、单次检索 vs 智能体 |
| MuSiQue 不可回答（缺一环） | 20 | 30 | 把一道可回答题的一篇证据页从所有语料中移除；再做语料级校验确认别处没有 |
| BRIGHT 可回答 | 40 | 80 | 检索召回、引用是否来自知识库（不评答案准确率） |
| BRIGHT 不可回答 | 10 | 20 | 证据网页移出语料 → 应答"知识库里没有" |
| NoLiMa | 20 | 38 | 答案（角色名）精确匹配；无字面线索的检索 |

- **闭卷过滤**：MuSiQue 候选题先让 Sonnet 5.5 闭卷回答，能答对的不选（Haiku 只是下限）。
- **中文**：每组约一半翻译成中文（Sonnet 5.5，专有名词保留英文）。
- **语料级校验**：沿用 v1 的校验流程，重点查不可回答题是否被其他文档泄漏。

### 1.7 P0.5 试跑后的设计调整（2026-11-10）
- **检索模式三种**：A0 单次检索（R2/R3/R4）、**A2 两轮检索**（检索 → 不足则联想出 1–3 个新查询再检索一次 → 仍没有就拒答；R2/R3）、A1 智能体（R1–R6，最多 12 步）。
- **system prompt**：智能体加入检索策略（先搜关键词，非英文问题同时用英文关键词；没结果就联想后再搜；多步问题逐块找；仍没有才拒答）。答题规则：具体事实必须来自知识库，可以用常识理解和串联知识库内容，不能用常识补缺。
- **NoLiMa 只评检索**（是否找到植入片段）：找到植入句后模型多数仍拒答——"住在旁边"不等于"去过"、且植入句在上下文中突兀——准确率反映的是推断意愿，不是检索。误拒率也不计 NoLiMa。
- **BRIGHT 不可回答题按体量判定有效性**（`kb2_validate_bright.py`，与评分一致的"能否实质性回答"标准）：S300 10/10、S900 27/30、S3000 24/30 有效。有效题共 415 道：S300 135、S900 414、S3000 412。
- **评分**用 Opus 5.5 Message Batches（半价）。
- **试跑实测单题成本（S3000）**：Sonnet A0 $0.018–0.032、A2 $0.045–0.059、A1 $0.026–0.076；Haiku 约为 Sonnet 的 1/10–1/20。P2 Claude 预估约 $620。

## 3. 检索方式（6 种）

| # | 方式 | 实现 | 单次检索 A0 | 智能体 A1 |
|---|---|---|:-:|:-:|
| R1 | **grep** | ripgrep + read_file 工具，模型自己决定搜什么、读什么（类似 Claude Code） | – | ✓ |
| R2 | **BM25** | SQLite FTS5 或 `bm25s`（纯 Python，无服务） | ✓ | ✓（作为 search 工具） |
| R3 | **混合检索** | BM25 + API embedding + RRF 融合；向量存为本地 `.npy`，numpy 暴力算余弦（3000 篇约 1 万个块，毫秒级），**无向量数据库、无 Docker** | ✓ | ✓ |
| R4 | **增强混合（QMD 式，全 API）** | Haiku 5.5 查询扩展 → BM25 + 向量 → RRF → `qwen3-reranker-8b`（OpenRouter `/rerank`）重排 → 按排名位置混合打分；**本地不放任何模型** | ✓ | ✓ |
| R5 | **LLM-wiki 导航** | 先 digest；模型读 `index.md` → 跟 wikilink 读页面，可在 wiki 内 grep | – | ✓ |
| R6 | **LLM-wiki + 混合** | digest 后的 wiki 页面用 R3 建索引；模型可以搜索也可以跟链接 | – | ✓ |

**P1 附带消融**（不进端到端）：纯向量检索、R3 换另一个 embedding 模型、R4 只开查询扩展、R4 只开重排。

**可行组合**：A0 下 3 种（R2、R3、R4）＋ A1 下 6 种 = **9 种检索配置**。

### 3.1 R3 和 R4 的区别（R4 = 用 API 复刻 QMD 的检索流程）

不直接用 QMD 产品：它需要在本地下载并管理约 2GB 的 GGUF 模型。R4 保留 QMD 的流程设计，把每个模型换成 API。

| | R3 混合 | R4 增强混合（QMD 式） | 原版 QMD（参考，不测） |
|---|---|---|---|
| BM25 | ✓ | ✓（同一个索引） | SQLite FTS5 |
| 向量 | `qwen3-embedding-8b`（API） | 同 R3 | 本地 embeddinggemma-300M |
| 查询扩展 | 无 | Haiku 5.5 生成 关键词版 / 语义版 / HyDE 假想文档版（固定模型，所有被测模型共用） | 本地 1.7B 微调模型 |
| 融合 | RRF | RRF（原始问题权重 ×2）+ 排名第一加分 | 同左 |
| 重排 | 无 | `qwen3-reranker-8b`（OpenRouter `/rerank`），取 RRF 前 30 名 | 本地 Qwen3-Reranker-0.6B |
| 混合打分 | – | 按 RRF 排名位置混合：第 1–3 名 75/25，第 4–10 名 60/40，第 11 名以后 40/60 | 同左 |
| 每次检索额外开销 | 一次 embedding | + 一次 Haiku 调用（约 $0.0005）+ 一次重排（约 $0.005） | 本机算力 |

R3 和 R4 共用同一套 BM25 与 embedding，差别只在查询扩展和重排，P1 消融可以分别算出两者的贡献。结论表述为"QMD 式检索流程"的效果，不代表 QMD 产品本身。

### 3.1.1 LLM-wiki 的生成方式（R5 / R6 的前置）
`scripts/digest_wiki.py`，两步：
1. **map（LLM，按文档缓存）**：Sonnet 5.5（effort medium）读每篇原文，输出 摘要、一句话简介、8–15 条自包含关键事实、实体（名称 / 类型 / 角色）、标签。实测 RepliQA $60.70、MultiHop $16.33。
2. **reduce（代码，每个体量各生成一份）**：
   - `index.md`：只列主题（3000 篇时单页列全部文档约 7.5 万 token，所以分两层）
   - `topics/<主题>.md`：该主题所有文档 + 一句话简介
   - `sources/<主题>/<文档>.md`：摘要 + 关键事实 + 实体双链 + 原文路径
   - `entities/<实体>.md`：仅为出现在 ≥2 篇文档的实体建页；被提到 >15 次的实体只列来源和角色
   - `raw/`：原文副本，wiki 里的原文链接可直接打开

| 体量 | 摘要页 | 实体页 | 主题页 |
|---|--:|--:|--:|
| S300 | 300 | 254 | 17 |
| S900 | 900 | 950 | 17 |
| S3000 | 3000 | 3559 | 17 |
| MultiHop | 609 | 1431 | 6 |

R6 的索引只覆盖 wiki 页面（摘要页 + 实体页 + 主题页 + index），不含 `raw/`。

### 3.2 Embedding（API，通过 OpenRouter，同一个 key）
| 候选 | 价格 | 备注 |
|---|---|---|
| **`qwen/qwen3-embedding-8b`**（默认） | $0.01 / M tokens | 多语言强，中英混合友好；**固定服务商 DeepInfra**（不同服务商同一文本的向量余弦约 0.997，语料与查询必须同源；Nebius 有每分钟 token 配额，大批量会 429） |

## 4. 模型

| 模型 | ID | 通道 | 价格（$/M tokens，输入未命中缓存 / 输出） | 环境变量 |
|---|---|---|---|---|
| Haiku 5.5 | `claude-haiku-5-5` | **Anthropic API** | 0.10 / 0.50 | `ANTHROPIC_API_KEY` |
| Sonnet 5.5 | `claude-sonnet-5-5` | Anthropic API | 2.00 / 10.00 | 同上 |
| （裁判）Opus 5.5 | `claude-opus-5-5` | Anthropic API | 4.00 / 20.00，Batch 半价 | 同上 |
| DeepSeek V4.1 Flash | `deepseek-flash` | **DeepSeek 官方 API** | 高峰 0.30 / 1.20，非高峰 0.15 / 0.60（缓存命中 0.006 / 0.003） | `DEEPSEEK_API_KEY` |
| 千问 3.8 Flash | `qwen/qwen3.8-flash` | OpenRouter（服务商：Alibaba） | 0.15 / 0.47 | `OPENROUTER_API_KEY` |

（价格取自 2026-11-10 的 DeepSeek 官方价格页和 OpenRouter `/api/v1/models`，跑实验时重新拉取。）

- **思考强度**：Claude 两个模型都设 `effort: medium`。DeepSeek 只支持 `low / high / max`，没有 medium，用默认的 `high`。千问用默认设置。全部记录在结果里。
- **DeepSeek 高峰时段**（UTC 周一至周五 01:00–04:00、06:00–10:00，即北京时间 09:00–12:00、14:00–18:00）价格翻倍，可能也更慢 → DeepSeek 批量跑尽量放在非高峰时段，每条结果记录时间戳。
- **Claude 速率限制**（每分钟）：45k 请求、10M 输入 token、2M 输出 token，并发不是瓶颈；为了延迟数据干净，计时类运行仍然串行或低并发。
- **通道差异**：Anthropic API、DeepSeek 官方、OpenRouter 三个通道的网络延迟不同，"时间"指标按通道分开报告，不直接横向比较绝对值。
- **OpenRouter key 每日限额 $300**：千问 Flash 完整阶段典型情景约 $80，一天内跑完（embedding 费用可以忽略）。
- 同一套 agent harness（自写工具循环），四个模型共用同样的工具定义和 system prompt。

## 5. 评测指标

| 目标 | 指标 | 计算 |
|---|---|---|
| **召回率** | 检索 Recall@5 / @10、MRR | 标准答案文档是否出现在检索结果中（A1 统计整个轨迹读过的文档） |
| **准确率** | 答案正确率 | Opus 5.5 当裁判（不在被测名单中，可走 Batch API 半价）+ 人工抽检 10% 校准 |

**拒答判分规则（已确认）**：

## 附录 A：v1 题库（RepliQA / MultiHop-RAG）为什么被放弃

**根因**：RepliQA 是阅读理解数据集，题目是看着单篇文档写的——英文题实词中位数 80% 原样出现在证据文档中
（MultiHop-RAG 84%），检索测的是"关键词能不能对上"，BM25 在 3000 篇中召回 100%。语料是互相独立的虚构文章，
没有个人知识库的真实难点（同一实体多篇笔记、版本冲突、信息分散、写法和问法不同）。
**补丁让问题更糟**：语料级校验剔除"有歧义"的题，等于筛掉难题；"模糊版"改写基于证据文档，又把关键词带回去。
**流程教训**：早期 BM25 97% 和 64% 的不可回答题泄漏都是红灯，应当立即停下重审数据集，而不是继续打补丁（约 $130 花在了 v1 上）。

以下为 v1 原文，留档：

### [v1] 1. 语料：公开数据集

#### [v1] 1.1 主线：RepliQA（ServiceNow，CC BY 4.0）
| 项 | 数据 |
|---|---|
| 规模 | 5 个 split，每个约 3,600 篇文档，**每篇 5 道题** |
| 篇长 | 约 1,000 词/篇（约 1.3k tokens），和真实 KB 的一篇文章量级接近 |
| 主题 | 17 类（公司制度、安全事件、本地新闻、政务、教育、菜谱……）→ 同主题文档天然互为**干扰文档** |
| 不可回答题 | 约 21%，`answer = "The answer is not found in the document."`（`long_answer = "NA"`；数据卡写的 `UNANSWERABLE` 与实际不符） |
| **关键优点** | 文档是人写的**虚构**内容（虚构人物/机构/地点），模型不可能凭训练记忆答对 → 准确率和拒答率测的是"真用了知识库" |

**为什么一个 split 就够**：一个 split ≈ 3,600 篇 > 3000，干扰文档问题自然解决，不需要额外造。

#### [v1] 1.2 副线：MultiHop-RAG（多跳 / 聚合 / null query）
- 609 篇新闻、2,556 道题，题型有 推理、比较、时序、**null query（库里没有）**。
- 用途：补 RepliQA 没有的**多跳题**，并测 LLM-wiki 在实体互相关联的语料上的价值（RepliQA 文档彼此独立，wiki 链接价值会被低估）。
- 风险：新闻是 2023 年的，模型可能见过 → 每道题先做**闭卷基线**（不给检索直接问），闭卷能答对的题标记出来单独统计或剔除。
- 只在原生体量（609 篇）跑，不参与 300/900/3000 的体量对比。

#### [v1] 1.3 转成 md 知识库的样子
数据集里是 JSON / parquet，但实验用的语料是**一篇一个 `.md` 文件**。为了让它更像个人 md 知识库：
- 加 frontmatter：`title`、`topic` / `category`、`date`、`source`（取自数据集元数据）
- 文件名用标题的 slug，不用随机 ID
- 文首加 `# 标题`；RepliQA 从 PDF 抽出来的"像标题的短行"转成 `##`

还是比不上真实 md 库的地方（报告要写明）：没有 `[[双链]]`、篇长很均匀（RepliQA 5.6k–9.8k 字符，真实库长尾到 24 万）、几乎没有表格和代码。

#### [v1] 1.4 P4 真实 md 库验证（待定）
候选：作者自己的团队 md 知识库（约 600 篇，frontmatter + 双链 + 表格 + 长尾篇长，正好落在 500–1000 篇区间）。最优几组配置加基线，用约 60 道 LLM 出题 + 人工抽查。
待定：是否做；如果做，只跑 Claude 还是四个模型都跑（内部文档发给 DeepSeek / 阿里云可能不合规）。

### [v1] 2. 体量与问题集设计

#### [v1] 2.1 体量构造（嵌套）
从 RepliQA 一个 split 中**随机**抽取：S300 ⊂ S900 ⊂ S3000。

#### [v1] 2.2 "标准答案全在 300 篇里会不会太少？"
- **不会有偏差**：S300 是随机抽样，它里面的文档和其他 2700 篇在统计上没有区别；检索器也不知道哪些是"S300 的"。
- **真正决定可信度的是题目数量**，不是有标准答案的文档有多少篇。
- **嵌套 + 同一套题**的好处：三个体量问的是**同一批题**，差异只来自干扰文档变多，可以做配对比较（McNemar 检验），比"每个体量各出一套题"灵敏得多。
- 你的思路（从题反推文档、按体量决定题数）会让三个体量的题不同，题目难度会和体量混在一起，所以只把它作为**补充**：S900 / S3000 各额外抽 50 道"标准答案文档在 S300 之外"的题做 sanity check，确认结论一致。

#### [v1] 2.3 主线问题集（每个体量 300 题，三个体量共用）

| 类别 | 题数 | 来源 | 测什么 |
|---|--:|---|---|
| 可回答 | 200 | RepliQA，标准答案文档在 S300 中 | 召回 / 准确 |
| 不可回答 A：文档在库里，但没有这个信息 | 50 | RepliQA 原生 UNANSWERABLE | 近似干扰下的拒答 |
| 不可回答 B：**整篇文档就不在库里** | 50 | 从**另一个 split** 取可回答题（文档不放入任何语料） | 最贴近真实的"库里没有" |
| 体量 sanity（仅 S900/S3000） | +50 | 标准答案文档在 S300 之外 | 验证无偏 |
| 英文模糊版（P0 新增） | +100 | 100 道英文可回答题的改写：去掉精确名字，用描述代替（`scripts/build_vague.py`，Sonnet 5.5），与原题配对 | 用户记不清原词时的检索 |

模糊版实测（S3000 Recall@10）：BM25 99%（原题 100%）、向量 95%（原题 87%）——**没有变难**。为了不产生歧义，改写必须保留 1–2 个能区分的细节（日期、地点、事件描述），这些细节本身就是很好的关键词；RepliQA 每篇讲的都是独特的虚构事件，"无歧义的题"几乎必然带字面线索。结论：检索方式之间的差距主要体现在跨语言（中文题）上，最终推荐按提问方式分别给出。

- **语言**：每类 50% 翻译成中文（Sonnet 5.5 翻译 + 自动校验专有名词保留英文），专有名词保留原文。
- **统计精度**：200 道可回答题，准确率 95% 置信区间约 ±6pp；配对比较可以分辨 8–10pp 的差异。不可回答题共 100 道，约 ±9pp。

#### 2.3.1 语料级效度校验（P0 新增）
RepliQA 是"一篇文档配 5 道题"写的，放进大库会出问题，所以每道题都要在 S3000（所有体量的超集）上校验：
BM25 + 向量检索各取前 6 篇候选（去掉标准答案文档），由 Sonnet 5.5 判断是否有其他文档能回答。
- 不可回答题被其他文档回答 → 剔除（leak）
- 可回答题被其他文档给出**矛盾**答案 → 剔除（ambiguous）；给出**一致**答案 → 补进标准答案文档
- 题干含 "according to the document" 一类默认只有一篇文档的说法 → 直接排除
- 剔除后从备选池补题，循环到没有新剔除为止（`scripts/build_questions.py` → `translate_questions.py` → `validate_questions.py`，结果按题号缓存）

首轮校验结果：**"文档里没有答案"类 64% 被剔除**（题目太泛，别的文档恰好讨论了），"整篇文档不在库里"类 22%，可回答题 4%。
原因：RepliQA 的不可回答题多是泛泛的问题；虚构名字在不同文档中大量复用且设定矛盾（如 "Maria Gonzalez" 出现在 196 篇中，"The Green Fork" 在两篇里老板不同）。

#### [v1] 2.4 副线问题集
MultiHop-RAG 抽 150 题（推理 / 比较 / 时序 / null 各占一定比例），中英各半。

#### [v1] 2.5 已知偏差（报告里要写明）
- RepliQA 的问题常带独特的专有名词 → **grep / BM25 会比真实场景表现好**（真实用户经常不知道精确术语）。中文提问能部分抵消这一点。
- RepliQA 文档彼此独立 → LLM-wiki 的跨文档链接价值主要看副线结果。
- **P0 实测印证**（S3000，Recall@10）：BM25 英文题 97% / 中文题 53%；向量检索 英文 81% / 中文 79%。英文题对关键词检索有天花板效应，检索方式之间的差异主要会在中文题上体现。
- RepliQA 常见虚构人名在大量文档中复用 → LLM-wiki 的实体页会把不同的人汇总到一起（真实知识库里同名人物/项目也有此风险）。
